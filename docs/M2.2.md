# M2.2: daily use on one machine

M2 and M2.1 work on the happy path (E2E-1). This milestone makes wf fit for **stage 1** (SPEC §1): one
developer using it every day on a real project, wf included. The review of 2026-10-12
([REVIEW-2026-10-12.md](REVIEW-2026-10-12.md)) lists what stands in the way; its groups A to C are the
work items here.

The bar: no off-path case leaves an item stuck without saying so, a daemon restart costs agent
context at most, the daemon can be run and inspected like a service, and the log can be exported.

## Decisions
* **What happens after a session fails is configured like reviews: recovery levels.** The policy
  holds an ordered list of named levels; each is a list of steps that run one after another, each
  time a session ends without finishing. A type names its default level, an item can name another.
  Steps for now:
  * `"retry"`: the dispatcher may start the item again (any agent that can take it).
  * `{ agent = { requires = [...] } }`: a **diagnose** session of an agent with those capabilities
    reads what happened and writes a comment on the item; the next attempt's brief carries it.
  * `"principal"`: the item waits in `wf inbox`, with why the last attempt ended.

  Commands as steps follow later ([HOOKS.md](HOOKS.md)).
* **Which step is next is computed, not stored.** It is the number of unsuccessful attempts (and
  diagnose sessions) of the item since it last moved on, as a pure function in `wf-core::lifecycle`.
  Nothing new goes into the log for it; the level can be changed at any time and applies at once.
* **An interrupted session is not a failed one.** A daemon that restarts ends its leftover sessions
  `Interrupted`; that uses up no step.
* **`principal`** always means the accountable person (SPEC §5): the review step and the recovery
  step that wait on them are both `principal`, and the review level with only that step is `manual`.
* **Agents run with `permissions = allow` by default**, inside Fence. A machine without a sandbox
  turns `allow` into `ask` (as built). README and SPEC say so.
* **The network is off until a workforce has a second device.** A daemon of a workforce with one
  device starts no iroh endpoint and no gossip; `wf invite` starts it.
* **The daemon's agents call the daemon's own `wf`.** At start the daemon copies its binary to
  `<data>/bin/wf` and puts that first on the `PATH` of its sessions, so rebuilding wf does not
  change the protocol that running agents speak.

## Recovery levels
```toml
[[recovery]]
name = "none"
steps = ["principal"]                       # the first failure waits for the principal

[[recovery]]
name = "standard"                           # `default` is reserved, as for review levels
steps = ["retry", "retry", "principal"]

[[recovery]]
name = "diagnose"
steps = [{ agent = { requires = ["review"] } }, "retry", "principal"]

[types.task]
recovery = "standard"
```
* **Attempts.** A session that ends `Released`, `TimedOut` or `Failed` is an unsuccessful attempt.
  `Interrupted` and `Cancelled` (stopped by the principal) are not. Giving up after the nudges ends
  `Released`, as now.
* **Per role, since the item last moved on.** Work attempts count since the last submission; review
  attempts count since the current submission, per step; supervise attempts since the blocker was
  written. So a reviewer that never gives a verdict runs into the level like a worker (R1 of the
  review), instead of being started again forever.
* **The principal resets it.** A `principal` step ends when the principal acts on the item: starts
  a session, comments, edits or moves it. The level then starts from its first step again.
* **Steps run out:** after the last step the item waits for the principal, as if the level ended in
  `principal`.
* **Diagnose sessions** are a new session role, `Diagnose`, run in an empty directory like
  supervise sessions. The brief has the item, its comments, and the ended attempts with their
  reasons and the agent's last words. The session comments and ends `Diagnosed`; that comment is
  listed in the next work brief under "what went wrong before".
* **Shown:** `wf item show` names the next step (`retry 2 of 2`, `waits for the principal: released
  by @joshua/coder: "cannot reach the registry"`); `wf status` counts items waiting after a failure;
  `wf inbox` lists them.
* This replaces `given_up_on` and `MAX_FAILED_SESSIONS` in `wf-core::dispatch`.

## Format changes
None that need a workforce to be recreated: signatures cover the encoded bytes, so a change to the
layout of a body cannot be carried over by an export either.
* `EndReason::Interrupted`, `EndReason::Diagnosed`, `SessionRole::Diagnose` and `Change::Recovery`
  are appended variants; old events still decode.
* An item's recovery level is set by `Change::Recovery` only, not by a field of `ItemCreated`.
  `wf item add --recovery` writes the edit right after the item.

## Work items
### A: no silent stalls
1. `EndReason::Interrupted` for sessions a restarting daemon ends.
2. Recovery levels in the policy, the `recovery` field on types and items, `wf item add|edit
   --recovery`, and the next step computed in `wf-core::lifecycle`; the dispatcher follows it for
   work, review and supervise sessions. Nudges and the give-up note depend on the session's role.
3. Diagnose sessions for the agent step.
4. A merge that fails after a session ends moves the item to its review state with a comment,
   like a waiting merge. An error after `SessionStarted` ends the session `Failed`.
5. Stopping is bounded: starting a harness watches for a stop, a cancelled turn has a timeout, a
   cancel is never lost, and held permission requests are answered `Cancelled` on cancel.
6. Claiming and starting a session is one storage job; ending a session is serialized per session;
   a merge checks whether its commit already landed before merging again.
7. A failed diff fails the review session instead of briefing an empty diff.

### B: running it
1. Agents run the daemon's own copy of `wf`.
2. `wf daemon start|stop|status`, a pid file, `tracing` to `<data>/daemon.log`, SIGTERM.
3. `wf status` says whether the daemon runs, what is live, parked or waiting after a failure, and
   what to do next.
4. `wf export` (and `wf import` of what it wrote) for backups and for reading the log with `jq`;
   the "remove the directory" hint only for a store that does not decode.
5. The network is off for a workforce with one device.

### C: the CLI
1. `wf item show --json` without duplicate keys; help for every command and flag; the `agent add`
   summary.
2. `permissions = allow` as the default everywhere.
3. `wf review --request-changes` moves the item through `wf-core`, as one decision, not two events.
4. Error messages that list the valid values; local times in `wf log`; empty lists say so.
5. `wf item cancel`, `wf agent remove`, `wf session list --live`, filters for `item list`.
6. Typed enums between `view` and `render`, without wildcard arms.
7. SPEC §17 describes the binary.

## As built
### A: no silent stalls (done)
* **Recovery** lives in `wf-core::recovery` (`State::recovery(item, role)`, `State::diagnosable`),
  not in `lifecycle`. Each failure takes the next step of the level, and so does each finished
  diagnosis; after the last step the principal decides. A step is taken per role; the agent step
  retries for review and supervise sessions, since only work is diagnosed.
* **"The principal acts on the item"** is any event of the principal's on it: created, edited,
  moved, linked, archived, commented on, a verdict. The fold keeps when that last happened
  (`Item::principal_touched`). Session starts are written by the daemon, so `wf session start`
  alone does not start the level again; a session started by hand that fails takes the next step.
* The default policy has the levels `none`, `standard` (tasks and distills) and `diagnose`.
  Workforces created before have none in their stored policy: their items wait for the principal
  after the first unsuccessful session until `wf policy edit` adds levels.
* Policies stored before the rename say `"human"` for the principal's review step; it still
  parses. A stored policy that this version cannot parse no longer makes the log unreadable: it is
  admitted, `wf status` flags it, and the workforce runs on the last policy that parses (or the
  default, for a genesis). The author still parses a policy before signing it. Snapshot format 7.
* A merge that fails after a session ends comments `Could not merge into <target>: …` and moves
  the item to its review state, where the dispatcher tries again. When the target is checked out,
  `git merge --ff-only` can fail after it updated the files (a held ref lock), which leaves the
  checkout dirty: the merge then waits as for any dirty checkout.
* Stopping is bounded: a harness has 3 minutes to start, a cancelled turn 20 seconds to end, and
  closing kills the harness's process group after 10 seconds. Cancels go through a `watch`, so an
  early one is not lost, and a held permission request is answered `cancelled`.
* Work starts take a per-item lock before the state is read; session ends take one lock for the
  daemon. A merge of a commit that is on the target already names the earlier merge.
* The golden genesis event uses a fixed policy text, so changing the default policy no longer
  changes it. The socket protocol is version 7.
* Not tested: a review session whose diff cannot be read fails (no cheap way to make `git diff`
  fail in the integration tests).

### B: running it (done)
* The daemon copies the `wf` it runs as to `<data>/bin/wf` when it starts (through a rename, so
  running agents keep the old file) and puts that directory first on the agents' `PATH`. A copy,
  not a hard link: in the tests, macOS killed runs of `target/debug/wf` while daemons linked it.
  The first run of a fresh copy takes about 2 seconds on macOS, so the session tests leave
  `wf_binary` unset and the fake agent calls `$WF_BIN`; a unit test covers the copy.
* `wf daemon start` spawns `wf daemon run` in its own process group, with its output appended to
  `<data>/daemon.log`, and waits for the socket. `run` writes `<data>/daemon.pid` and stops on
  Ctrl-C or SIGTERM; `stop` sends SIGTERM and waits for the process. The daemon logs through
  `tracing` (filter in `WF_LOG`, default `warn,wf_daemon=info,wf_net=info,wf_cli=info`).
* `wf status` adds `daemon`, `ready_items`, `live_sessions`, `parked_sessions`, `after_failures`
  (one line per item left to the principal, as on `item show`), `waiting_on_you` and one `next`
  step: add an agent, start the daemon, `wf inbox`, `wf watch` or add an item.
* `wf export` writes one JSON line per event: `id`, `kind`, `content` (the signed content with the
  body as its fields) and `event` (the canonical bytes, base64). `wf import` reads only `event`,
  checks every signature again, and creates the store if there is none; it refuses while the
  daemon runs, and refuses forks for now. Keys are not exported.
* The old hint said to remove the workforce's directory, which holds its `principal.key`. It now
  shows only for a store that does not decode and names `store.redb`.
* The node starts on first use. Each workforce goes online once it has another device or an
  unused, unexpired invite (re-checked whenever its heads change); joining and following start
  the node as well. A workforce loaded while the node is up is served at once, so a fork can be
  followed right after it was made.
* Found on the way: when the socket path is longer than `SUN_LEN` (a long `XDG_RUNTIME_DIR`),
  every command failed instead of falling back to the store. Fixed in group C.

### C: the CLI (done)
* `wf item show --json` takes `lane` and `labels` from the summary only. A test walks the command
  tree and fails on any command, argument or flag without help; `agent add` showed the help of
  the flattened autonomy flags, which now sit under their own heading.
* `allow` was already the default in the code; only the README said `ask`.
* A `RequestChanges` verdict moves the item to the first open state of its type in the fold, as
  `Supersedes` does for its target; `wf review` writes no `ItemMoved` after it. Snapshot format 8.
* Unknown types, states, lanes, review and recovery levels and agents name the valid ones
  (`OneOf` in `wf-core::validate`). `item list --type`, `--state` and `--lane` refuse names no
  item can have instead of printing nothing. `wf log` and the last-seen times are local; every list
  that can be empty already said so.
* `wf item cancel` moves an item to its type's cancelled state. A work session closes after its
  turn once its item is anywhere but open or active (review, done, cancelled, the backlog, or
  archived), not only in review. `wf agent remove` writes the new `AgentRemoved` (tag 8): the
  agent becomes a tombstone (`Lww<Option<AgentDefinition>>`), so its sessions' events stay valid
  in any order, and defining it again brings it back. It refuses while the agent has live sessions.
  Protocol 8, snapshot format 9. `wf session list --live` and `item list --label`, `--lane` and
  `--priority` are new.
* `render` matches on typed values: `StateCategory`, `Priority`, `CommentKindView`,
  `ActivityKind`, and `ReviewStatusView`, which is now a tagged enum. `SourceView.origin` became
  `in_comment`, and workforce events in `wf watch --json` have the kind `workforce`. JSON schema 3.
* Renamed: `WaitsOn::Principal`, `Waiting::PrincipalReview` (inbox kind `principal_review`),
  `PrincipalCannotEscalate`; the agent prompts say "your principal".
* SPEC §17 lists the commands as built, with the ones still planned under *Later*.
