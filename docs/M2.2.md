# M2.2: daily use on one machine

M2 and M2.1 work on the happy path (E2E-1). This milestone makes wf fit for **stage 1** (SPEC §1): one
developer using it every day on a real project, wf included. The review of 2026-10-12
([REVIEW-2026-10-12.md](REVIEW-2026-10-12.md)) lists what stands in the way; its groups A to C are the
work items here.

The bar: no off-path case leaves an item stuck without saying so, a daemon restart costs agent
context at most, the daemon can be run and inspected like a service, and the log can be exported.

## Decisions
* **What happens after a session fails is configured like reviews: recovery levels.** The policy
  holds an ordered list of named levels; each is a list of steps that run one after another, each
  time a session ends without finishing. A type names its default level, an item can name another.
  Steps for now:
  * `"retry"`: the dispatcher may start the item again (any agent that can take it).
  * `{ agent = { requires = [...] } }`: a **diagnose** session of an agent with those capabilities
    reads what happened and writes a comment on the item; the next attempt's brief carries it.
  * `"principal"`: the item waits in `wf inbox`, with why the last attempt ended.

  Commands as steps follow later ([HOOKS.md](HOOKS.md)).
* **Which step is next is computed, not stored.** It is the number of unsuccessful attempts (and
  diagnose sessions) of the item since it last moved on, as a pure function in `wf-core::lifecycle`.
  Nothing new goes into the log for it; the level can be changed at any time and applies at once.
* **An interrupted session is not a failed one.** A daemon that restarts ends its leftover sessions
  `Interrupted`; that uses up no step.
* **`principal`** always means the accountable person (SPEC §5): the review step and the recovery
  step that wait on them are both `principal`, and the review level with only that step is `manual`.
* **Agents run with `permissions = allow` by default**, inside Fence. A machine without a sandbox
  turns `allow` into `ask` (as built). README and SPEC say so.
* **The network is off until a workforce has a second device.** A daemon of a workforce with one
  device starts no iroh endpoint and no gossip; `wf invite` starts it.
* **The daemon's agents call the daemon's own `wf`.** At start the daemon copies its binary to
  `<data>/bin/wf` and puts that first on the `PATH` of its sessions, so rebuilding wf does not
  change the protocol that running agents speak.

## Recovery levels
```toml
[[recovery]]
name = "none"
steps = ["principal"]                       # the first failure waits for the principal

[[recovery]]
name = "standard"                           # `default` is reserved, as for review levels
steps = ["retry", "retry", "principal"]

[[recovery]]
name = "diagnose"
steps = [{ agent = { requires = ["review"] } }, "retry", "principal"]

[types.task]
recovery = "standard"
```
* **Attempts.** A session that ends `Released`, `TimedOut` or `Failed` is an unsuccessful attempt.
  `Interrupted` and `Cancelled` (stopped by the principal) are not. Giving up after the nudges ends
  `Released`, as now.
* **Per role, since the item last moved on.** Work attempts count since the last submission; review
  attempts count since the current submission, per step; supervise attempts since the blocker was
  written. So a reviewer that never gives a verdict runs into the level like a worker (R1 of the
  review), instead of being started again forever.
* **The principal resets it.** A `principal` step ends when the principal acts on the item: starts
  a session, comments, edits or moves it. The level then starts from its first step again.
* **Steps run out:** after the last step the item waits for the principal, as if the level ended in
  `principal`.
* **Diagnose sessions** are a new session role, `Diagnose`, run in an empty directory like
  supervise sessions. The brief has the item, its comments, and the ended attempts with their
  reasons and the agent's last words. The session comments and ends `Diagnosed`; that comment is
  listed in the next work brief under "what went wrong before".
* **Shown:** `wf item show` names the next step (`retry 2 of 2`, `waits for the principal: released
  by @joshua/coder: "cannot reach the registry"`); `wf status` counts items waiting after a failure;
  `wf inbox` lists them.
* This replaces `given_up_on` and `MAX_FAILED_SESSIONS` in `wf-core::dispatch`.

## Format changes
None that need a workforce to be recreated: signatures cover the encoded bytes, so a change to the
layout of a body cannot be carried over by an export either.
* `EndReason::Interrupted`, `EndReason::Diagnosed`, `SessionRole::Diagnose` and `Change::Recovery`
  are appended variants; old events still decode.
* An item's recovery level is set by `Change::Recovery` only, not by a field of `ItemCreated`.
  `wf item add --recovery` writes the edit right after the item.

## Work items
### A: no silent stalls
1. `EndReason::Interrupted` for sessions a restarting daemon ends.
2. Recovery levels in the policy, the `recovery` field on types and items, `wf item add|edit
   --recovery`, and the next step computed in `wf-core::lifecycle`; the dispatcher follows it for
   work, review and supervise sessions. Nudges and the give-up note depend on the session's role.
3. Diagnose sessions for the agent step.
4. A merge that fails after a session ends moves the item to its review state with a comment,
   like a waiting merge. An error after `SessionStarted` ends the session `Failed`.
5. Stopping is bounded: starting a harness watches for a stop, a cancelled turn has a timeout, a
   cancel is never lost, and held permission requests are answered `Cancelled` on cancel.
6. Claiming and starting a session is one storage job; ending a session is serialized per session;
   a merge checks whether its commit already landed before merging again.
7. A failed diff fails the review session instead of briefing an empty diff.

### B: running it
1. Agents run the daemon's own copy of `wf`.
2. `wf daemon start|stop|status`, a pid file, `tracing` to `<data>/daemon.log`, SIGTERM.
3. `wf status` says whether the daemon runs, what is live, parked or waiting after a failure, and
   what to do next.
4. `wf export` (and `wf import` of what it wrote) for backups and for reading the log with `jq`;
   the "remove the directory" hint only for a store that does not decode.
5. The network is off for a workforce with one device.

### C: the CLI
1. `wf item show --json` without duplicate keys; help for every command and flag; the `agent add`
   summary.
2. `permissions = allow` as the default everywhere.
3. `wf review --request-changes` moves the item through `wf-core`, as one decision, not two events.
4. Error messages that list the valid values; local times in `wf log`; empty lists say so.
5. `wf item cancel`, `wf agent remove`, `wf session list --live`, filters for `item list`.
6. Typed enums between `view` and `render`, without wildcard arms.
7. SPEC §17 describes the binary.
