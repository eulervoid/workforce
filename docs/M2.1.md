# M2.1: convenience at the CLI

M2 works end to end, but a person still does too much by hand: every permission request waits for
`wf session allow`, reading the work of an item means finding its worktree, review comments are typed
one `wf comment` at a time, and what waits on you only shows when you run `wf inbox`. M2.1 fixes that
before any TUI is built: first make the CLI as convenient as it can be.

```bash
wf watch                          # events scroll by; a blocker, a review or a permission request prompts you
wf item diff k3f7                 # the work, in your pager or difftool
wf item checkout k3f7             # the main checkout at the head of wf/k3f7, detached
wf review k3f7 --annotate         # comment in the diff (lumen), each comment becomes a change request
```

## Decisions
* **Permission requests go through a chain of deciders**, each of which may answer or pass:
  built-in rules, then the device's hook, then the judge, then a person. A fixed `allow` or `deny`
  of the agent skips the chain. Every decider sees the same request.
* **Hooks and the judge are configured per machine, never in the signed policy.** A command is only
  meaningful on the machine that has it, and policy that syncs must not make other machines run
  programs. The config is `$XDG_CONFIG_HOME/workforce/config.toml` (`MachineConfig`), the first
  machine-local config wf has.
* **The judge is an agent, run like any other.** It is a harness session in the `permissions` lane,
  so wf still never handles model credentials or calls a model API itself. It runs in an empty
  directory and every permission request it makes is denied.
* **Annotated review produces ordinary change requests.** The diff tool is configurable. Its output
  is split into one change request per annotation, so nothing in the log is specific to lumen.
* **`wf watch` polls**, as `wf session watch` does. A subscription call on the socket can come with
  the TUI.

## Work items

### 1. Built-in rules: a session may always run `wf`
A request that only runs `wf` (the command, its arguments, nothing chained after it) is allowed for
every agent whose permissions are `ask`. Agents report back through `wf`, so asking about it only
slows them down. For that the runner needs the tool call itself, not only its title:
`HeldPermission` carries `kind`, `title` and the raw input of the ACP tool call.

### 2. Permission hook
```toml
# $XDG_CONFIG_HOME/workforce/config.toml
[permissions]
hook = ["my-judge", "--strict"]   # argv, no shell
timeout = "20s"                   # then the request passes on
```
* The daemon starts the hook for each request and writes one JSON object to its stdin: workforce,
  item (id, title, type, state), session, agent and its capabilities, the working directory, and the
  tool call (`kind`, `title`, raw input, the offered options).
* The hook prints one JSON line: `{"decision": "allow" | "deny" | "ask", "reason": "..."}`. `ask` passes
  the request on. A crash, a timeout or output that does not parse passes it on too, and the daemon
  logs why.
* The decision, who made it and the reason go into the session's transcript, so `wf session show`
  tells why something was allowed.
* `wf permissions test < request.json` runs the chain without a session, to try out a hook.

### 3. The judge
```bash
wf agent add judge --harness claude-code --lane permissions --start auto
```
```toml
[permissions.judge]
agent = "judge"
guidance = """
Allow reading anything and writing inside the worktree. Allow cargo, git without push.
Ask about network access, anything outside the worktree, and deleting files.
"""
```
* The daemon keeps one live judge session per machine and prompts it once for each request that gets
  this far. Each prompt holds the guidance, the request and the item. The judge answers with the same
  JSON line as the hook. The session is replaced after `turns` prompts (default 50), so its context
  stays small.
* What the judge decides is written to the transcript of the session that asked, as for the hook.
* `wf inbox` shows the requests the judge passed on with its reason. That also shows whether the
  guidance is right.

### 4. Diff and checkout
* `wf item diff <item>` shows the diff through the git pager. `--stat` gives a summary, and `--tool`
  opens it with `git difftool` (or `[diff] tool` in the machine config).
* `wf item checkout <item>` switches the main checkout, detached, to the head of the item's branch.
  It cannot switch to the branch itself, because that is checked out in the item's worktree. It is
  refused when the checkout is dirty. `wf item checkout -` goes back to where you were.
* `wf item path <item>` prints the worktree of the item, for `cd $(wf item path k3f7)`.
* A worktree is removed after the merge, so `checkout` and `path` say where the work went (merged as
  `<commit>`) instead of failing.

### 5. Annotated review
```toml
[review]
annotate = ["lumen", "diff", "{base}..{head}"]
```
* `wf review <item> --annotate` runs the tool on the submitted commit and reads what it prints.
  lumen prints its annotations on stdout and draws its UI on `/dev/tty`.
* The output is split into annotations. Each becomes a change request on the item, with the file and
  lines it is about at the start of its text. Then the verdict is `RequestChanges`. With no annotations
  it asks whether to approve.
* The split depends on the tool: a parser for lumen's format, and the whole output as one change
  request for any other tool.
* Without a tool configured, `--annotate` opens the diff in `$EDITOR`. Lines you add that start with
  `>` become change requests on the hunk above them.

### 6. `wf watch`
* It prints the events of the workforce as they arrive, one line each, with the summaries that item
  activity already has: `14:02  #k3f7  @joshua/coder · ⧗ blocker → @joshua  c7f2`.
* When something waits on you, it stops and asks. For a blocker it asks for an answer, which becomes
  a comment that resolves it. For a permission request it asks to allow or deny. For a human review
  step it offers to approve, to request changes (through `--annotate`), to show the diff or to skip.
* Skipped prompts come back on the next start. Piped output only prints, it never prompts.
* `--item <item>` follows one item.
