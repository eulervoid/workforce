# M2.1: convenience at the CLI

M2 works end to end, but a person still does too much by hand: every permission request waits for
`wf session allow`, reading the work of an item means finding its worktree, and what waits on you only
shows when you run `wf inbox`. M2.1 fixes that before any TUI is built: first make the CLI as convenient
as it can be.

```bash
wf watch                          # events scroll by; a blocker, a review or a permission request prompts you
wf item diff k3f7                 # the work, through git, so your pager and delta apply
wf item checkout k3f7             # the main checkout at the head of wf/k3f7, detached
```

## Decisions
* **Permission requests go through a chain of deciders that you order yourself.** Each decider
  either answers or passes the request on. A person comes after all of them. A fixed `allow` or
  `deny` of the agent skips the chain.
* **Three kinds of decider besides the built-in rules:** a hook (any program), an agent (a harness
  session) and a decision model such as Jev, from whichever host serves it. Each kind can appear in the chain more than once, for example a
  cheap model first and a stronger judge after it.
* **The machine config holds the deciders, never the signed policy.** A command is only meaningful
  on the machine that has it, and policy that syncs must not make other machines run programs or call
  paid APIs. The config lives in `$XDG_CONFIG_HOME/workforce/config.toml` (`MachineConfig`), the first
  machine-local config wf has.
* **Every hook speaks JSON.** wf writes one JSON object to the hook's stdin and reads one JSON
  object from its stdout. Both sides ignore fields they do not know, so either side can add fields
  later. The input names the hook and its version, `{"hook": "permission", "version": 1, ...}`. This
  applies to every hook wf will have, including the later scheduler hook.
* **wf runs git for diffs instead of copying its output.** The user's pager, `delta`, colours and
  diff settings then apply as they do for `git diff`. There is no `--tool` flag of wf's own.
* **`wf watch` polls**, as `wf session watch` does. A subscription call on the socket can come with
  the TUI.

## Work items

### 1. Built-in rules: a session may always run `wf`
A request that only runs `wf` (the command, its arguments, nothing chained after it) is allowed for
every agent whose permissions are `ask`. Agents report back through `wf`, so asking about it only
slows them down. For that the runner needs the tool call itself, not only its title:
`HeldPermission` carries `kind`, `title` and the raw input of the ACP tool call.

### 2. The machine config and the chain
```toml
# $XDG_CONFIG_HOME/workforce/config.toml
[permissions]
guidance = """
Allow reading anything and writing inside the worktree. Allow cargo, and git without push.
Ask about network access, anything outside the worktree, and deleting files.
"""

[[permissions.decider]]
kind = "rules"

[[permissions.decider]]
kind = "model"
url = "https://api.typesafe.ai/v1/systemone"
model = "jev-latest"
api_key_env = "TYPESAFE_API_KEY"
# allow above one threshold, deny below the other, pass on in between
question = { noul = { allow_above = 0.95, deny_below = 0.05 } }

[[permissions.decider]]
kind = "hook"
command = ["my-judge", "--strict"] # argv, no shell
timeout = "20s"

[[permissions.decider]]
kind = "agent"
agent = "judge"
```
* Deciders run in the order listed. A request that every decider passes on goes to a person.
  Without a config the chain is `rules`, then the person.
* A decider passes on when it says `ask`, crashes, times out or answers with something that does not
  parse. The daemon logs the cause.
* The request every decider sees is the same JSON: workforce, item (id, title, type, state),
  session, agent and its capabilities, the working directory, the tool call (`kind`, `title`, raw
  input, the offered options) and the guidance.
* The decision, the decider that made it and its reason go into the transcript of the session that
  asked, so `wf session show` tells why something was allowed. `wf inbox` shows, next to a request
  that reached you, why each decider passed it on.
* `wf permissions test < request.json` runs the chain without a session, to try out a configuration.

### 3. Hook
* It gets the request on stdin and prints
  `{"permission": "allow" | "deny" | "ask", "reason": "..."}`.
* Any check fits here, such as a script with an allowlist, a company proxy or a call to some other
  model.

### 4. Decision model (Jev)
* A decision model is called over the System One API: `POST` to the configured `url` with
  `Authorization: Bearer <key>` and `{"model", "state", "questions"}`, answered with `{"answers": ...}`.
  Hosts serve it at different paths, so the config names the whole endpoint, and there is no list of
  providers in wf:

  | Host | `url` | `model` |
  |---|---|---|
  | TypeSafe | `https://api.typesafe.ai/v1/systemone` | `jev-latest` |
  | OpenRouter | `https://openrouter.ai/api/v1/systemone` | `typesafe/jev-1.13` |
  | Cloudflare Workers AI | `https://api.cloudflare.com/client/v4/accounts/<account>/ai/run/@cf/cloudflare/clef` | `clef` |

  Cloudflare wraps its responses in `{"result": ...}`, so `answers` is read from either level.
* The state the model decides on is the guidance and the request. The config sets what it is asked
  and how the answer becomes a decision:
  * `noul`: "Should this tool call be allowed?" It answers with a probability, which is compared with
    two thresholds: allow above `allow_above`, deny below `deny_below`, pass on in between.
  * `choice`: which of `allow`, `deny` and `ask` fits. The pick is taken when its confidence is at
    least `min_confidence`, and passed on otherwise; a pick of `ask` passes on too.

  ```toml
  question = { noul = { allow_above = 0.95, deny_below = 0.05 } }
  question = { choice = { min_confidence = 0.8 } }
  ```
  `question` is an enum in `MachineConfig`, so each way carries only the settings it uses.
* Answers take well under a second, so a model in front of an agent or a person saves most of the
  waiting.
* The API key is read from the environment variable the config names. wf keeps it in memory only and
  sends it only to `url`. This is the first model API wf calls itself; harness credentials stay
  with the harnesses.
* The request and response are those of TypeSafe's API reference. OpenRouter documents the same
  fields, and Cloudflare's Clef follows the System One API as a drop-in for Jev. A host with a
  different API can always be put behind a hook.

### 5. Agent
* The daemon keeps one live session per machine of the agent the config names, prompts it once for
  each request that reaches it, and expects the same JSON as from a hook. The session is replaced
  after `turns` prompts (default 50), so its context stays small.
* It runs in an empty directory, and every permission request it makes itself is denied.

### 6. Diff and checkout
* `wf item diff <item>` runs `git diff <target>...<commit>` in the main checkout with the terminal as
  its stdout, so git pages and formats it as configured (`core.pager`, `pager.diff`, `delta`). Flags
  that are not wf's own go to git: `wf item diff k3f7 --stat`, `-- src/`. With `--json`, or when not
  at a terminal, it prints the plain diff as now.
* `wf item checkout <item>` switches the main checkout, detached, to the head of the item's branch.
  It cannot switch to the branch itself, because that is checked out in the item's worktree. It is
  refused when the checkout is dirty. `wf item checkout -` goes back to where you were.
* `wf item path <item>` prints the worktree of the item, for `cd $(wf item path k3f7)`.
* A worktree is removed after the merge, so `checkout` and `path` say where the work went (merged as
  `<commit>`) instead of failing.

### 7. `wf watch`
* It prints the events of the workforce as they arrive, one line each, with the summaries that item
  activity already has: `14:02  #k3f7  @joshua/coder · ⧗ blocker → @joshua  c7f2`.
* When something waits on you, it stops and asks. For a blocker it asks for an answer, which becomes
  a comment that resolves it. For a permission request it asks to allow or deny. For a human review
  step it offers to approve, to request changes, to show the diff or to skip.
* Skipped prompts come back on the next start. Piped output only prints, it never prompts.
* `--item <item>` follows one item.

## Later
* **Annotated review:** `wf review <item> --annotate` runs a configured diff tool such as lumen, and
  each annotation becomes a change request. lumen prints its annotations on stdout and draws its UI on
  `/dev/tty`; how its output splits into single annotations is still to be checked. Without a tool,
  the diff opens in `$EDITOR`, and added lines that start with `>` become change requests on the hunk
  above them.
* A TUI with the live state of the workforce, built on what `wf watch` shows.
* A comment can name a file and lines as data, not only in its text, when a TUI or the origin has a
  use for it.

## As built
* All of items 1 to 7 are built, in that order. `wf permissions test` takes a request as JSON on
  stdin, or `--command` to make one up around a shell command; an agent decider only decides in the
  daemon, so the test passes it on.
* The built-in rule allows `wf item`, `comment`, `work`, `review`, `inbox`, `status`, `log`, `search`
  and `mentions`, alone or piped into `head`, `tail`, `grep`, `rg`, `wc`, `sort`, `uniq`, `cut` or
  `jq`, with `2>&1` and redirections to `/dev/null`. Anything it does not understand, such as `;`,
  `&&`, substitutions, other redirections or `wf agent`, is passed on. `wf session allow` is not
  among them, so an agent cannot answer its own request.
* The machine config is read for each request, so changes apply without restarting the daemon. A
  config that does not parse sends requests to a person, with why in the inbox.
* A model decider sends the whole request as the state and asks one question named `permission`.
  TLS uses rustls with ring, the provider the rest of the build already has. A test against
  TypeSafe with a made-up key gets its 401 (`cargo test -p wf-daemon -- --ignored`).
* An agent decider is no wf session: nothing about it goes into the log. Its transcript is
  `transcripts/judge-<agent>.jsonl` next to the others, and it runs in `judges/<agent>`.
* `wf item diff`, `checkout` and `path` show the head of the item's branch, which is the latest
  work, and what was submitted once the branch is gone. `--json` after the item is wf's flag, not
  git's.
* `wf watch` shows the last 10 events, then polls the daemon twice a second. It needs the daemon.
  A review prompt offers the diff, approval, and change requests one per line, then the verdict.
  Notices for proposals and merges are shown once per run.
