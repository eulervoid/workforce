# M2: agents at work (one machine)

## Goal
Agents work through the items of a workforce on one machine without being watched. The daemon starts
harnesses over ACP, keeps them going until their item is submitted, routes their questions to a
supervisor agent or to the human, has the work reviewed at the level the item asks for, and merges it
locally. How much happens without the human is configured per agent, per type and per item.

```sh
wf agent add coder --harness opencode --capabilities rust --start auto
wf agent add reviewer --harness claude-code --capabilities review,strong-model --start auto
wf agent add supervisor --harness claude-code --lanes supervision --start auto
wf item add --title "Parse durations in policy" --review standard
wf daemon &                               # dispatches: coder takes the item
wf session list                           # coder on #k3f9 (in_progress), 12 min
wf session watch k3f9                     # follow the transcript
# coder asks with `wf work ask`, parks; supervisor answers or escalates
wf inbox                                  # escalated questions, human review steps, permission requests
wf item move q7x2 answered --note "Use humantime"   # the parked coder resumes
# coder runs `wf work submit`; reviewer reviews the branch; the daemon merges wf/k3f9 into main
wf item show k3f9                         # done · merged 3e1a9c0 · reviewed by @joshua/reviewer
```

## Scope
| In | Out (later) |
|---|---|
| Sessions: one attempt by one agent at one item, `SessionStarted`, `SessionEnded` | sessions on several devices of one workforce: anchor dispatch, `Assigned`, `Claim`, leases (M3) |
| One branch and worktree per item, sessions continue the branch | `Heartbeat` and liveness across devices (M3) |
| ACP runner in the daemon (opencode, claude-code, codex, gemini-cli) | `raw-cli` fallback (M3) |
| Turn-end handling: nudge, park, end; limits | `wf` MCP server; agents use the CLI (M3) |
| Local dispatcher, per agent `start = auto \| manual` | session inboxes, mentions delivered into live sessions (M3) |
| Questions with `wf work ask`, the `supervision` lane, `needs_human` | overlap notifications from the files commits touch (M3) |
| Review levels in the policy, `review` on items, `Review` events, `wf review` | merge mode `origin`: push, pull requests, `Merged` from origin (M3) |
| Local merge into the target branch, `Merged` | secret brokering, redaction of transcripts (M3) |
| Permission requests answered per agent: `allow`, `ask`, `deny` | permission requests answered by a supervisor |
| `wf inbox` for what waits on the human | a scripted scheduler hook; harness plugins |
| Checklist progress derived from item bodies, `Report` events with `wf work report` | `distinct_principal` for reviews (M5, with several principals) |

## Concepts
| Concept | Meaning |
|---|---|
| **Item** | A piece of work sized for one session. Steps inside it are a markdown checklist in the body. Split into separate items only when the parts can run in parallel, need a different review level, or need different capabilities. |
| **Session** | One attempt by one agent at one item, on this device. It holds the item's claim while it is live. |
| **Branch** | `wf/<item>`, in the worktree `<data>/<workforce>/worktrees/<item>`. Successive sessions on the item continue it. Removed after the merge. |
| **Supervisor** | An agent whose `lanes` include `supervision`. It answers questions or escalates them to the human. No extra rights: lanes route, members are trusted. |
| **Review level** | A named entry of the ordered `[[review]]` list in the policy: a sequence of steps, each an agent matched by capabilities or the human. An item without a level is not reviewed. |

## Format changes
All in the first work item. Existing workforces are recreated.

* **New body tags:**

  | Tag | Body | Payload |
  |---|---|---|
  | 20 | `SessionStarted` | `agent: AgentName`, `item: ItemId`, `role: SessionRole` (`Work` or `Review{commit}`) |
  | 21 | `SessionEnded` | `session: SessionId`, `reason: EndReason` |
  | 22 | `Review` | `item`, `commit: CommitId`, `verdict: Verdict`, `note: Option<String>` |
  | 23 | `Merged` | `item`, `reviewed: CommitId`, `commit: CommitId` (the merge commit) |
  | 24 | `Report` | `session: SessionId`, `note: String`, `step: Option<StepId>` |

  ```rust
  enum EndReason {
      Submitted { commit: Option<CommitId> },  // work done; None when the branch has no commits
      Reviewed,                               // a review session gave its verdict
      Released,                               // gave up: `wf work release`, or nudges used up
      Blocked,                                // the item entered a blocked state (escalated question)
      TimedOut,                               // parked too long, or `max_duration` reached
      Failed,                                 // harness exited or failed, daemon restarted
      Cancelled,                              // `wf session stop`, or the claim went to another session
  }
  enum Verdict { Approve, RequestChanges, Escalate }
  enum CommitId { Git(GitOid) }               // the single `vcs` variant from SPEC section 9
  ```
* **`AgentDefined`** gains `autonomy: Autonomy`: `start: StartMode` (`auto | manual`, default `manual`),
  `nudges: u32` (default 3), `park_timeout` (default `2h`), `max_duration: Option<Duration>` (default none)
  and `permissions: PermissionMode` (`allow | ask | deny`, default `ask`). Set with `wf agent add|edit`.
* **`ItemCreated`** gains `review: Option<ReviewName>`; `Change` gains `Review(Option<ReviewName>)`.
* Tags for `Assigned`, `Claim` and `Heartbeat` are left for M3.

## Policy changes
```toml
[merge]
mode = "local"            # local | origin (M3)
target = "main"

[[review]]
name = "light"
steps = [{ agent = { requires = ["review"] } }]

[[review]]
name = "standard"
steps = [{ agent = { requires = ["review", "strong-model"] } }]

[[review]]
name = "critical"
steps = [{ agent = { requires = ["review", "strong-model"] } }, "human"]

[lanes.supervision]
claim = ["member"]
types = ["question"]

[types.task]
review = "standard"       # optional default level for items of this type

[types.question]
lane = "supervision"      # "default" or `initial = "needs_human"` routes questions straight to the human
states = [
  { name = "open",        category = "open" },
  { name = "needs_human", category = "blocked" },
  { name = "answered",    category = "done" },
  { name = "dropped",     category = "cancelled" },
]
```

* `[[review]]` is ordered from least to most strict. The position is what "lower" and "raise" mean.
  Parsing refuses duplicate names, a `review` key that names no level, and a type with a `review`
  default but no `blocked` state.
* The old `[review]` table (`approvals`, `distinct_principal`) goes: steps say how many approvals.
* Policy types: `MergeConfig { mode: MergeMode, target }`, `ReviewLevelConfig { name, steps }` with
  `enum ReviewStep { Agent { requires: BTreeSet<Requirement> }, Human }`, `TypeConfig.review`.
* The bundled default policy defines the three levels and the `supervision` lane but sets no default
  level on `task`, so a fresh workforce works without reviewer agents.
* **A type's open, active, blocked and done state** is the first state in its list with that category.
  The runner moves items with these; built-in behaviour keeps keying on categories, never on names.

## Sessions
* **Start:** the daemon writes `SessionStarted{agent, item, role}` (actor: the device's principal) and
  moves a work item to the type's active state, if it has one. Its id is the session id.
* **Live** means started and not ended. On one machine nothing else is needed: the daemon knows its
  processes, and on start it ends every live session of its own device with `Failed` and reopens their
  items. Leases for sessions of other devices come in M3.
* **The claim** belongs to the earliest live work session of an item by `(hlc, EventId)`. Two
  daemons that start a session on the same item converge: the later one cancels its session
  (`Cancelled`). This is the only multi-device rule in M2.
* **Ready**: open, all dependencies done, no live session. An open item with its dependencies done
  and a live session is `Readiness::Claimed`.
* **Ending** a work session moves its item:

  | Reason | Item goes to |
  |---|---|
  | `Submitted`, review level set, commits on the branch | the type's blocked state, review begins |
  | `Submitted`, no review level, commits on the branch | merged, then the type's done state |
  | `Submitted`, no commits | the type's done state, with the submit note (a question's answer) |
  | `Blocked` | stays in the blocked state the agent moved it to |
  | `Released`, `TimedOut`, `Failed`, `Cancelled` | the type's open state; the branch stays for the next session |

## Agents in a session
The runner starts the harness with `WF_SESSION=<session id>` in its environment. The CLI reads it,
writes as `Actor::Agent{agent, session}`, and the daemon refuses it unless the session is live and runs
on this device. Commands for agents live under `wf work` and fail outside a session (no `WF_SESSION`):

| Command | Effect |
|---|---|
| `wf work submit [--note]` | the work is finished: ends the session `Submitted{head}` |
| `wf work ask "<question>" [--body]` | creates a question, makes the session's item depend on it; the session parks at turn end |
| `wf work release [--note]` | gives up: ends the session `Released`, comment with the note |
| `wf work report "<text>" [--step <number> [--done]]` | writes a `Report` for the session (SPEC section 10); `--done` also ticks the step. The step must exist in the item's body. |
| `wf item ...`, `wf comment`, `wf review` | as for humans, within the guards below |

**Guards** (`State::check_actor`, an authoring check for agent actors next to `check_policy`; mistakes and
shortcuts, not attacks, since members are trusted and keys are on disk). Admission only checks that the
session exists and runs on the author's device; whether it is live depends on arrival order, so the
author checks that too:
1. A session cannot move a question it asked to a done state.
2. A session cannot lower the review level of an item its agent has worked on. Supervisors and humans can.
3. Agent actors cannot write `AgentDefined` or authority bodies.
4. A session cannot move its own item to a done state; it uses `wf work submit`.
5. `Review` comes from a review session on that item and commit, or from a human. A reviewer agent never
   had a work session on the item.
6. A `Report` comes from a live session of this device, and `step` is only allowed in a work session. The
   item is the session's, so a report cannot name another.

## Runner
One task per session in the daemon, behind a `Harness` trait with one ACP implementation (ACP v1, the
`agent-client-protocol` crate).

| Harness | Command |
|---|---|
| `opencode` | `opencode acp` |
| `claude-code` | `claude-agent-acp` |
| `codex` | `codex-acp` |
| `gemini-cli` | `gemini --experimental-acp` |

* `initialize` probes installation and login; `wf agent list` shows the result. `wf init` detects the
  ACP commands instead of the bare binaries.
* The client advertises no `fs` or `terminal` capabilities: harnesses use their own tools in the worktree.
* `session/new` in the worktree, then `session/prompt` with the **work package**: title, body, the
  dependencies with their final notes, answers to its questions, comments, reports and review notes of
  earlier attempts, the branch, and the agent rules (commit small on this branch, check items off in the body, report what you chose and why with `wf work report` (not required),
  finish with `wf work submit`, ask with `wf work ask`, give up with `wf work release`). A review session gets the
  item, the commit, `git diff <target>...<commit>`, its step and the `wf review` commands.
* `session/update` is appended to `<data>/<workforce>/transcripts/<session>.jsonl`, local and
  unpublished. `wf session watch` follows that file.
* `session/request_permission` is answered by the agent's `permissions`. `ask` holds the request in
  the daemon (runtime state, lost with the process), shows it in `wf inbox`, and waits for
  `wf session allow|deny <session>`.
* `session/cancel` on `wf session stop`, on `max_duration`, and when the claim is lost.

### Turn end
When `session/prompt` returns, a pure function in `wf-core` decides what happens next, from the state,
the session, the nudges used and the clock:

```rust
enum TurnOutcome {
    Close,       // the session already ended (`wf work submit`, `wf work release`), or its item is blocked
    Park,        // the item waits on a dependency, such as its own question
    Continue,    // prompt again: "continue; submit, ask or release when you are done or stuck"
    GiveUp,      // nudges used up without a new commit: end `Released` with a comment
}
```

* Nudges count consecutive turns without a new commit on the branch; a commit resets the count.
* A **parked** session keeps its harness process and conversation and counts against `max_sessions`.
  It is prompted again with the answers when its item is ready again, or ends `TimedOut` after
  `park_timeout`. An item moved to blocked closes the session with `Blocked`.

## Dispatcher
A daemon loop, woken by heads changes, session ends and a 30 s tick (timeouts). For every agent this
device hosts (`DeviceProfile.agents`) with `start = auto` and a free slot (device and agent
`max_sessions`, parked sessions included):

1. **Reviews first:** an item awaiting an agent step whose `requires` the agent meets, and on which the
   agent never worked. Starts a review session.
2. **Then work:** the first ready item in the agent's lanes whose `requires` the agent's capabilities
   plus the device's hardware meet, ordered as `wf item list --ready`. Starts a work session.

The selection is a pure function in `wf-core`, shared with `wf item list --ready --for <agent>`.
`start = manual` agents run only through `wf session start <item> --agent <name>`. A level step that no
hosted agent can take is flagged in `wf status`.

## Review and merge
The **review status** of an item is computed at query time from the latest `Submitted{commit}` work
session, the item's level and the `Review` events on that commit:

```rust
enum ReviewStatus {
    Awaiting { step: ReviewStep },   // the next step without a verdict
    ChangesRequested,
    Approved { commit: CommitId },
    Merged { commit: CommitId },
}
```

* Steps run in order. `Approve` moves to the next step. `Escalate` (agents only) inserts a `Human` step
  right after the current one.
* `wf review <item> --request-changes --note` writes the `Review` and moves the item to the type's
  open state; the next work session continues the branch with the note in its work package. The next
  submission starts the level from its first step.
* A verdict names its commit, so **what was reviewed is what gets merged**. A verdict on an older
  commit counts for nothing.
* **Local merge** (`[merge] mode = "local"`), once approved:
  1. `git merge-tree --write-tree <target> <commit>`. On a conflict: comment, move the item to the
     type's open state; the next session merges the target into the branch, and the review starts over.
  2. `git commit-tree` with both parents: `Merge #k3f9: <title>`.
  3. If the target is checked out in a worktree, it must be clean: `git merge --ff-only` there.
     Otherwise `git update-ref` with the old value, so a concurrent change of the target fails safely.
     A dirty checkout makes the merge wait, shown in `wf inbox`.
  4. `Merged{item, reviewed, commit}`, the item to the type's done state, worktree and branch removed.
* `wf item diff <item>` shows `git diff <target>...wf/<item>` for human review steps.

Git is called as the `git` CLI (2.38 or later for `merge-tree --write-tree`) behind the `VcsAdapter`
trait. gix has no merge yet; check again when this is built.

## Inbox
`wf inbox` lists what waits on the human, newest first:
* items in a blocked state that are not under review, such as questions in `needs_human`;
* items awaiting a `Human` review step;
* permission requests held by the daemon;
* merges waiting on a dirty checkout.

## Testing
* **Pure:** turn outcome, dispatch selection and review status over generated states; every guard with
  a refusing and an accepting case; claims and review status do not depend on event arrival order.
* **Git:** worktrees, continuing a branch, clean merge, conflict, dirty checkout, a target moved during
  the merge.
* **Runner:** a fake ACP agent driven by a script (commit, call `wf`, end the turn, ask for permission,
  hang, crash) against a real daemon in a temporary repo, covering every row of the session end table.
* **End to end:** a question answered by a supervisor resumes the parked worker; an escalated one is
  answered from `wf inbox`; changes requested lead to a second session on the same branch; a daemon
  restart ends its sessions and the item is dispatched again.

## Exit criteria
* An item on this repo goes from `open` to merged in `main` with no human action: an opencode coder
  works it, a reviewer on a different model approves it, the daemon merges it.
* A `critical` item stops at the human step and merges after `wf review --approve`.
* A question asked mid-session is answered by the supervisor and the same session continues with its
  context; an escalated question appears in `wf inbox`.
* A killed harness and a restarted daemon leave no live sessions, and the next session continues the branch.
* Each of the four harnesses completes a small item at least once (manual, recorded under *As built*).

## Risks
| Risk | Mitigation |
|---|---|
| ACP adapters (`claude-agent-acp`, `codex-acp`, gemini's experimental mode) change under us | pin versions in docs, probe at start, opencode (native ACP) first |
| Agents ignore the protocol and never submit | nudges, then `Released` with a comment; the work package states the rules |
| Runaway cost | `start = manual` and `permissions = ask` by default, `max_duration`, nudges count only turns without commits |
| Merging into a checked-out branch loses local changes | only fast-forward a clean checkout, otherwise wait; never touch a dirty one |
| Parked sessions hold slots and memory | `park_timeout`; parked sessions shown in `wf session list` |
| Two daemons dispatch the same item before M3 | earliest session keeps the claim, the other cancels itself |

## Decided
* One item per session. Larger work is a larger item with a checklist; a planner splits only for
  parallelism, review level or capabilities.
* One branch per item; sessions are attempts that continue it.
* Stuck sessions park with a timeout instead of ending.
* wf orders ready items; agents choose within their item and create new ones freely.
* LLM scheduling happens through items (planners and supervisors), not inside the dispatcher.
* Supervisors are agents in the `supervision` lane; questions route by lane or initial state.
* Review levels live in the policy as an ordered list; the item names one, defaulting per type, and no
  level means no review. A reviewer is always a different agent from the author.
* A merge needs no separate setting: a level with a `Human` step waits for the human.
* Merging is local in M2; `origin` is the second `MergeMode` variant, in M3.
* Autonomy fields are part of the agent definition.
* No heartbeats in the log while sessions run on one machine.
