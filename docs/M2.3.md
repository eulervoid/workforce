# M2.3: the dashboard

With M2.2 wf runs every day on one machine, but keeping an eye on it takes several commands: `wf
status`, `wf inbox`, `wf item list`, `wf session watch`, and `wf watch` for what arrives. This
milestone puts all of it in one place: a terminal dashboard that the principal keeps open, for
example in a multiplexer pane next to the editor, and from which they answer what waits on them.

The bar: with the dashboard open, the principal never needs another `wf` command to see what the
workforce does or to answer what waits on them.

## Decisions
* **`wf watch` becomes the dashboard.** At a terminal it opens the dashboard; piped or with `--json`
  it prints the event stream as now. The line prompts of `wf watch` go away: the dashboard answers
  what they answered. `--item <item>` opens the dashboard on that item.
* **Built with `ratatui` and `crossterm`**, `tui-input` for the one-line input. It lives in
  `wf-cli/src/dashboard/`, and renders the view models of `wf-cli::view`; it computes nothing that
  a command could not show as well.
* **Tabs, each a list and a detail.** Narrow windows show one at a time: `enter` opens the detail,
  `esc` goes back. From 120 columns the detail sits right of the list and follows the selection.
  Everything is laid out for 60 columns and more.
* **The first tab is about acting.** It shows what waits on the principal, what is running and what
  is stuck; every action there is one key on the selected line.
* **The transcript gets a model.** `transcript.rs` is split into a structured transcript (turns,
  prose, tool calls, and a live tail that still changes) and the two things that draw it: the line
  printer of `wf session watch` and a ratatui widget. Feeding the printer's ANSI output to the TUI
  would freeze running calls and the width at the time they were printed.
* **Polling stays.** The dashboard asks the daemon for the state and new events every 500 ms, as
  `wf watch` does. A push subscription waits until polling shows up as a cost.
* **Only transcripts of this machine.** A session of another device shows its state and activity,
  and `transcript on <device>`; carrying transcripts is M3.
* **App state is pure.** The dashboard is a state struct updated by messages (a key, a refresh with
  the new state and events, a transcript tail), and drawing is a function of it. Tests drive it with
  messages and snapshot ratatui's `TestBackend` with insta, without a terminal or a daemon.
* **Selections hold ids, not row numbers**, so a refresh that adds or removes rows keeps the
  selection on the same item, session or agent.
* **Errors go to the footer.** A failed action or a daemon that stops answering is shown in the
  status line; the dashboard keeps running and tries again on the next refresh.

## Layout
Narrow, on the first tab:
```
 workforce          1 Now·3  2 Items  3 Agents  4 Log
 3 live · 14 open · 1 blocked · 2 devices
──────────────────────────────────────────────────────
 WAITING ON YOU
▸? coder on #k3j1 wants: rm -rf target        a / d
 ⧗ #x7k2 blocker from coder
   "Should the span live on ParseError or Loc…"
 ◎ #ab4c review 3e8a1c  +84 −12

 WORKING
 ◆ coder     #k3j1 Parse config lazily         12m
   ⠋ cargo test -p wf-core
 ◇ coder     #x7k2 Fix error spans     parked  40m
 ◆ reviewer  #ab4c Archive by category          2m

 NEEDS ATTENTION
 ! #q9r1 stranded: #m2n3 was cancelled
──────────────────────────────────────────────────────
 07:04 coder submitted 3e8a1c → in_review
 enter open · a allow · d deny · ? keys
```
* **Header:** the workforce, the tabs with the number waiting on the principal on the first, and one
  line of counts: live sessions, open and blocked items, devices seen.
* **Footer:** the latest event, then the keys that work on the selection, or an error, or the input
  of a reply.
* **Keys on a line** are shown only on the selected one, so the list stays quiet.
* **Glyphs** tell what a line is about. What waits on the principal is marked by its kind: `?`
  permission request, `⧗` blocker, `◎` review. A session is a diamond: `◆` running, `◇` parked.
  `!` is something flagged, `▸` the selection.

The detail of a session, opened from a session, an in-progress item or a permission request:

## Tabs
1. **Now.** *Waiting on you* is `wf inbox`: permission requests, blockers, principal reviews,
   proposals, merges and recovery. *Working* is the live sessions, parked ones marked, each with
   what it does now: the running tool call, or the last line of prose. *Needs attention* is what
   `wf status` flags: stranded items, unstaffed reviews, agents that never start. `enter` opens the
   session or item a line is about.
2. **Items.** `wf item list --group-by`: `o` cycles grouping by state, lane, priority and type;
   `/` filters on the title; `F` cycles through all, ready, blocked and stranded items. The detail is `wf item show`:
   header, body, steps, open comments, activity, and the item's sessions, which open the session.
3. **Agents.** Each agent with its sessions running against the sessions this machine gives it
   (`2/2 busy`, `0/1 idle`). The detail is the definition, its sessions with how each ended, and
   its stats.
4. **Log.** The event stream of today's `wf watch`, scrollable; `/` filters on an item.

## Keys
| Key | Where | Does |
|---|---|---|
| `1`–`4`, `tab`, `shift-tab` | everywhere | switch tabs |
| `j` `k` `↑` `↓`, `g` `G` | lists | move, top, bottom |
| `enter`, `esc` | everywhere | open the detail, go back |
| `?`, `q` | everywhere | keys, quit |
| `o`, `/`, `F` | Items tab | grouping, title filter, readiness filter |
| `a`, `d` | permission request | allow, deny |
| `r`, `R` | blocker | answer in the footer, in `$EDITOR` |
| `v` | principal review | approve, request changes (`$EDITOR`, one per line) or diff |
| `D` | item with work | the diff through git, in its pager |
| `s`, `x` | item, session | start a session (pick the agent), stop it |
| `m`, `c`, `e` | item | move (pick the state), comment, edit in `$EDITOR` |
| `f`, `G` | session | full transcript, follow the end |

`$EDITOR` and the git pager run with the dashboard suspended: it leaves the alternate screen,
restores the terminal, and draws again when they exit.

## Stats
Computed in `wf-core` from the state and the log, the clock passed in, so they are tested like the
rest of the fold:
* **Project:** items done in the last 7 days, the median time from the first session to done, the
  share of work sessions that ended without submitting, change requests per merged item.
* **Per agent:** sessions, the share that finished, the median duration.

The project line sits on the Now tab under the counts; the per-agent stats in the agent's detail.
A Stats tab follows only if there is more to show than that.

## Format changes
None. No new events, no new daemon calls.

## Work items
### A: transcript model
1. `wf-cli::transcript` folds entries into a `Transcript`: closed turns, prose, finished and open
   tool calls with their permission answers, and the tail that may still change. Pure, tested on
   the existing transcripts in the tests.
2. The line printer draws from the model, with the output of `wf session watch` unchanged
   (existing snapshots stay as they are).
3. `Transcript::now()`: what the session does at this moment, for the Now tab.

### B: the dashboard, read-only
1. `wf watch` at a terminal opens the dashboard: app loop, refresh every 500 ms, terminal restored
   on exit and on panic. Header, tabs, footer; `q` quits.
2. The layout rule: list and detail, side by side from 120 columns.
3. The Now tab and its three sections, with the session and item details.
4. The Log tab. `wf watch --item` opens the item.

### C: answering
1. Permission requests: `a` and `d`, in the Now tab and the session detail.
2. Blockers: `r` in the footer, `R` in `$EDITOR`, with suspend and resume.
3. The session detail follows its transcript live; `f` and `G`.
4. Principal reviews: `v` and `D`.
5. The line prompts of `wf watch` go.

### D: items
1. The Items tab: grouping, filter and toggles.
2. The item detail as `wf item show`, sessions opening the session detail.
3. `s`, `x`, `m`, `c`, `e`.

### E: agents and stats
1. The Agents tab and the agent detail.
2. Stats in `wf-core`, the project line on the Now tab and the per-agent stats.

### F: docs
1. SPEC §17 and §18: `wf watch` is the dashboard; README shows it.

## As built
All of A to F are built, in that order.
* **Transcripts.** `transcript::Transcript` folds entries into blocks that are only ever appended,
  plus the open paragraph and the open calls. `transcript::Layout` draws one block or the open part
  for a width; `Printer` (what was `Renderer`) prints new blocks as they come for `wf session watch`,
  whose snapshots did not change. The dashboard lays the whole transcript out again for the pane's
  width at each frame and turns the escape codes into ratatui text with `ansi-to-tui`, so nothing is
  frozen at the width or the moment it was first drawn. `transcript::Reader` follows a file for
  both.
* **Data.** The app owns what only grows: the transcripts of this machine's live sessions and of
  the session on screen, and the last 1000 lines of the event stream. Everything else is a
  `Snapshot`, taken at each refresh and after each key, of only what is on screen: item rows while
  the Items tab is, agents and stats while the Agents tab is, the open detail. `wf watch`'s activity
  lines are worked out once for each item instead of each event, which a backlog of 200 needed.
* **Keys.** The keys on what waits act on the selected entry, on the permission request of a
  selected or open session, or on what waits about the selected or open item. `s`, `m`, `c` and `e`
  act on the item of the selection or of the open detail, and `x` on a live session after `y`. The
  footer names the keys of what is selected; `?` shows all of them.
* **Actions** write the same events as the commands, through `dashboard::act`: the commands print,
  which would draw over the dashboard. `$EDITOR` is used for `R` (the answer above a scissors line,
  the blocker quoted below it), for the change requests of `v r` (one per line) and for `e`; `D`
  shows the diff in git's pager and waits for a key, since a short diff is printed without one.
  `s` and `m` ask the loop for the choices, which the app shows as a list to pick from.
* **Item detail:** `enter` opens the item's live session, else its latest; its other sessions are
  in its activity. A session detail has `i` for its item.
* **Agents tab:** each agent with its live sessions and the last five that ended, with how and
  how long ago; sessions open on their transcript, an agent on its definition and its stats. The
  project stats head this tab, not the Now tab: on a narrow pane, the Now tab keeps its lines for
  what needs acting on.
* **Stats** are `State::project_stats(now_ms)` and `State::agent_stats(agent)` in
  `wf-core::stats`: items done in the last seven days and the median time from their first work
  session to done, work attempts and how many failed (interrupted and cancelled sessions are no
  attempts), change requests per merged item; per agent its sessions, how many finished or failed,
  and the median time an ended session ran.
* `wf watch` without a terminal prints the event stream as before, without prompts.
