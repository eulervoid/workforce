# End-to-end run 1: a supervisor and a worker build a TypeScript CLI

Date: 2026-10-11. Machine: macOS, one device. Binary: `wf` built from `main` plus the uncommitted
Fence sandbox (`crates/wf-daemon/src/sandbox.rs`). Everything lived in a throwaway directory with its
own `XDG_DATA_HOME`, `XDG_CONFIG_HOME` and `XDG_RUNTIME_DIR`.

## Setup

* `git init` repo, `wf init --name demo --no-agents`.
* Policy: `[types.task] review` changed from `principal` (a human) to `light` (any agent with the
  `review` capability), so that no human has to review.
* Agents, both `claude-code`, `--model claude-haiku-5-5`, `--permissions allow`, `--start auto`,
  `--max-duration 25m`:
  * `supervisor`: capabilities `planning`, `review`; lanes `default`, `supervision`
  * `worker`: capability `typescript`; lane `default`
* `wf device edit --max-sessions 2 --agent supervisor=1 --agent worker=1`
* Machine config: `[sandbox]` (Fence, `code` template extended with the worktree, the repo `.git` and
  the daemon socket).
* One item by me: "Plan the project" (`--requires planning --review none`) describing a `todo-stats`
  CLI, asking the supervisor to split it into 3-5 items with `wf item add` / `wf item link`.

## Result

The project was built and works. 4 work items, each worked by the worker, reviewed and approved by the
supervisor, merged by the daemon.

| Item | Worker | Review | Notes |
|---|---|---|---|
| plan (me) | supervisor, 2 sessions | none | first session released (sandbox bug, below) |
| project setup | 22:26 | approved in 8 s | merge blocked 8 min by my own repo state, see bug 1 |
| markdown task parser | 22:35, 23 s | approved in 10 s | |
| summary and list, `--json` | 22:36, 23 s | approved in 18 s | |
| README | 22:36, 24 s | approved in 11 s | |

Final repo: 237 lines of TypeScript, 12 tests passing (`npm test`), `summary`, `list --open`, `--json`,
usage and error exit codes all behave as the README says. Output sample:

```
/tmp/sample.md: 1/3 [###-------] 33%
total: 1/3 [###-------] 33%
```

The agents ran on `node --test`, no runtime dependencies. One inaccuracy slipped through review:
`package.json` says "Compute statistics from TODO comments" while the tool reads markdown task lists.

I intervened three times (all listed below as bugs): restarted the daemon after the socket fix,
started the planning session by hand because the dispatcher does not retry a released item, and
committed `.workforce.toml` to unblock the merge.

## Bugs and inconsistencies

Ordered by how much they hurt.

1. **`wf init` leaves `.workforce.toml` untracked, which blocks every merge.** The first approved item
   waited 8 minutes (`merge: 6f2e3bce is ready to merge, but main is checked out with changes`). Nothing
   says which changes, or that the untracked marker file is the cause. A clean repo plus `wf init` should
   not make main dirty. Options: `wf init` commits it, writes it into `.git/info/exclude`, or the dirty
   check ignores it. At minimum the message should name the files.
2. **`--model` on an agent is stored but never used.** The harness gets no model selection: the ACP
   transcript shows `currentValue":"default"` and no `set_model`/`set_config_option`; all sessions ran the
   harness default, not Haiku. Either send it (ACP session config option, or an env var for the harness)
   or refuse the flag for harnesses that cannot honour it.
3. **An agent without lanes does nothing, silently.** `wf agent add worker --start auto` followed by
   `wf device edit --agent worker=1` produced no sessions and no warning. `wf item list --ready --for
   worker` printed `no items`. The cause was an empty lane list; `--lane default` fixed it. Same trap in
   the other direction: `--lane supervision` on the supervisor *replaced* the implicit default lane, so it
   could not take the planning item. Suggest: default `lanes = [default]`, and have `wf status` flag
   agents that can take no item.
4. **`start = auto` is not enough; the device must also host the agent.** Defining an auto agent and
   starting the daemon does nothing until `wf device edit --agent name=N`. Nothing points there. Also
   `max_sessions` defaults to 1 per device. `wf status` should say "agent X is auto but hosted on no
   device". A single-machine workforce could host all agents by default.
5. **Released items are never retried, and nothing says so.** After the first (sandbox-blocked) planning
   session was released, the item stayed `open` and ready, but the dispatcher skipped it. Only
   `wf session start` helped. `wf item show` should show "released by X, start manually" (the docs say
   this is by design, the CLI does not).
6. **Socket path limit.** A long `XDG_RUNTIME_DIR` gave `error: socket failed: path must be shorter than
   SUN_LEN`, printed by a command (`wf policy show`) that was not about sockets, after `wf init` had
   already "succeeded" printing `no agents defined`. Say which path and what the limit is.
7. **Sandbox (my change) first blocked `wf` itself.** Connecting to the daemon socket from inside Fence
   needs `network.allowUnixSockets`; writable alone is not enough. Fixed in `sandbox.rs`. The failure
   mode was good evidence for the design: the agent hit `socket failed: Operation not permitted`, tried
   several times to work around it (including "retry outside the sandbox"), and released. A sandbox error
   inside an agent session is invisible to the human: `wf session list` just says `released`.
   `wf session show` should say why (last agent message, or failure class).
8. **Actors are misleading.** Merges, state moves and dependency completions are attributed to
   `@ada` ("@ada · merged as fe550f94", "@ada · #5uk5ny done"), i.e. to the human, though the
   daemon did them. Item activity should say `daemon` (or `@ada/daemon`).

## Ergonomics

What worked well:

* The flow is easy to follow once agents exist: `wf item list`, `wf session list`, `wf inbox` are
  compact and consistent, status symbols (`○ ◐ ◎ ✓`) read at a glance.
* `wf item show` is the best screen: checklist, dependency links ("required by"), a timeline with step
  checks, the worker's note, the review verdict with its note, merge id. A reviewer's note read like a
  real review (ran the tests, noted two non-blocking points).
* `wf log` ends with `87/87 events verified`, a nice trust signal.
* The merge-blocked message in `wf inbox` appears in the right place, only too vague (bug 1).
* Sandboxing with Fence cost nothing noticeable: `npm install` and the model API worked through the
  allowlist, writes outside the worktree were denied, worktrees were removed after merging.

What was confusing or noisy:

* `wf session watch` starts with nine `log [session/create] ... phase=... durationMs=...` lines from the
  harness. Hide `agent_log` unless `--full`.
* Every tool call prints `? permission for <command>` then `✓ allowed by the agent's permissions`, even
  with `permissions = allow`. That is noise; print nothing for auto-allowed calls, or collapse them.
* The tool-call header is always the literal `$ Terminal`; it should name the tool or the command.
* The `wf log` columns truncate in a way that hides content: `ItemEdited ... #ts3hxo step` does not say
  which step; `SessionEnded` shows a raw `Submitted { commit: Some(Git(GitOid(6f2e3bce...` Rust debug
  string.
* The five step checks of a worker land within 15 ms of each other right before `submit` (the agent
  ticks them all at the end), so the timeline cannot be used as progress while work runs. Not a bug, but
  `Report`s (`wf work report`) are not used by agents at all because the prompt does not mention them.
* `wf session list` shows finished and failed sessions forever, newest first, with no `--live` filter or
  limit. Fine now, noisy later.
* Fresh workforce: nothing tells a new user the order `agent add` → `lane` → `device edit` → `daemon`.
  `wf status` should print a "next step" hint (no device hosts an agent / agent has no lanes / daemon not
  running).
* `--lane` and `--capability` are repeated flags (`--capability a --capability b`); the M2 doc examples
  show `--capabilities a,b`, which does not exist.
* The daemon prints one line at startup and then nothing: no log of sessions started, merged, or failed.
  Everything was reconstructed from `wf log` and the transcripts. A line per dispatch/merge would have
  saved time.

## How the supervisor behaved

* Planning: 4 well-scoped items with checkbox steps, correct dependency chain
  (setup → parser → commands → README), `--requires typescript` set on each. Took about 70 s.
* The supervisor never had to answer a question or merge anything itself; merging is the daemon after an
  approval, review is a separate review session (role `review`) of the same agent. So "supervisor decides
  merging" is really "supervisor's `light` approval triggers merge". It never requested changes, even
  where it noticed two small issues (it called them non-blocking). With Haiku-class reviewers, approvals
  are quick (8-18 s) and lenient; the `package.json` description mismatch is the evidence.
* The review sessions ran `npm test` and the CLI, so they were not rubber stamps.

## Costs and timings

* Wall clock from first working session to last merge: about 15 min, of which 8 min was bug 1 and about
  2 min bug 7. Pure agent time per item: 20-25 s work + 10-18 s review.
* Token use of a worker session, from the transcript: about 130k total, mostly cached reads
  (10 uncached input, 3.6k output).

## Suggestions, in order

1. Make `wf init` not leave main dirty; name the dirty files in the merge message (bug 1).
2. Apply `--model` or reject it (bug 2).
3. Default lanes and hosting so that `wf agent add x --start auto` just works on a one-machine workforce;
   make `wf status` diagnose the rest (bugs 3, 4).
4. Show the reason a session ended `released`/`failed` in `wf session show`; show it on the item (bugs 5, 7).
5. Attribute daemon actions to the daemon (bug 8).
6. Quiet `session watch` (log lines, auto-allowed permissions, `$ Terminal`), and give the daemon a log.
7. Land the sandbox: `[sandbox]` in `config.toml`, tests and the socket fix are in the working tree,
   uncommitted.
