# Review, 2026-10-12: how close is `wf` to daily use on one machine?

Scope: all seven crates (about 36k lines), the docs, and a hands-on session with a fresh build in a
throwaway workforce (`init`, `agent add`, `item add|show|move|archive`, `comment`, `daemon`, `watch`,
every `--help`). The test suite is green: 409 passed, 4 ignored. Findings marked **(verified)** were
checked against the code or reproduced; the rest come from careful reading and are very likely but
not reproduced.

## Bottom line

**The happy path works, and it is closer than it feels.** E2E-1 built a small TypeScript project with
a supervisor and a worker, reviewed and merged it without a human, and most of its eight bugs were
fixed the same day. The data model is sound and well tested: event log, fold, admission, review
levels, lifecycle as pure functions. **What stands between today and "I use this every day for real
work" is not missing features. It is what happens off the happy path.** These are the cases a
single developer hits in the first week:

1. **Restarting or rebuilding the daemon hurts.** Running sessions are ended as `Failed`, three
   failures make the dispatcher drop the item for that agent for good, and a rebuilt `wf` with a new
   protocol version breaks the `wf` that running agents call. Because wf is developed with wf, this
   is the most frequent case of all.
2. **Several paths strand work silently.** A released item is never retried. A reviewer without a
   verdict is re-dispatched forever. A failed merge leaves an item `Active` with no session. A
   stopped session can hang.
3. **The daemon is a foreground process with `eprintln!` as its only log**, and nothing in the CLI
   says whether it runs or what it is doing.
4. **No `wf export`**, while the daemon's advice for an unreadable store is "remove the directory".
   The log is the only truth, and on one machine there is no peer to restore it from.

Fix those four groups, about two milestones' worth of small commits, and wf is usable daily for
real work on one machine. CLI polish (help text, naming, filters) is the next layer and is mostly
cheap.

## What is strong (keep it)

* **The split between `wf-core` and everything else.** The admission/fold split, CRDT merge rules,
  `lifecycle::after_end`, `dispatchable` and `reviewable` are pure and testable. The exhaustive
  `EventBody` matches in fold, activity and `check_actor` pay off.
* **Sync written against generic streams and `SyncLog`**, with a 1,000-schedule simulation and fork
  tests.
* **Single-writer storage.** Appends, pending events and snapshots commit in one redb transaction.
* **The CLI's best screens are good.** `wf item show` (checklist, links, activity timeline), `wf log`
  ending in `N/N events verified`, and the compact `item list` / `session list` / `inbox` tables.
* **Permission chain and sandbox.** Ordered deciders, JSON hooks, machine config kept out of the
  signed policy, and Fence by default are a coherent design.

## 1. Blockers for daily use (ranked)

### 1.1 Restarts and rebuilds
* **A restart counts as a failure (verified).** `end_stale_sessions` ends live sessions with
  `Finish::Failed` (`wf-daemon/src/runner.rs:978`). `given_up_on` stops dispatching an item to an
  agent after 3 failed sessions (`wf-core/src/dispatch.rs:106-124`). Three restarts during one item
  and the agent silently stops taking it. Fix: add an `EndReason::Interrupted` (or use
  `Cancelled`) that does not count.
* **A rebuild breaks running agents.** The runner puts the daemon's exe directory first on the
  agents' `PATH` (runner.rs:1068-1076). After `cargo build`, agents call the new `wf`. The socket
  protocol requires an exact version match (`proto.rs:22`, `server.rs:20`), so `wf work submit`
  fails until the daemon restarts, and the restart then ends every conversation (above).
  * Short term: copy the daemon's own binary to `<data>/bin/wf` at startup and put that on agents'
    `PATH`, so agents always speak the daemon's protocol.
  * Later: resume conversations with ACP `session/load` where a harness supports it, and offer
    `wf daemon restart --when-idle`.

### 1.2 Work that gets stuck silently
* **A released item is never retried (verified).** `Released` and `TimedOut` make `given_up_on`
  return true forever for that agent (dispatch.rs:113). The nudge give-up also ends `Released`. With
  one coder agent, which is the normal solo setup, any give-up leaves the item "ready" in
  `wf item list --ready` while nothing will ever start it. E2E-1 bug 5 is still open.
  * Minimum: `wf item show` and `wf status` should say "given up by @x/coder; `wf session start`
    to retry".
  * Better: a cool-down or a retry budget instead of a permanent ban.
* **A reviewer with no verdict loops (verified).** `reviewable` (`wf-core/src/review.rs:185-218`)
  has no given-up check, unlike `dispatchable`. A reviewer that never commits runs out of nudges,
  is `Released`, and is dispatched again on the next heads change, for as long as tokens last. The
  nudge text also tells reviewers to `wf work submit` (runner.rs:1184). Nudges and give-up should
  depend on the session's role.
* **A failed merge leaves the item stuck (verified).** In `finish_session` the `MergeThen` error is
  kept, `SessionEnded` is still written, and the error is returned afterwards (runner.rs:684-736).
  The item stays `Active` with no session, and `pending_merges` only looks at review-category
  states, so nothing picks it up again. Any git hiccup (`index.lock`) triggers this. Fix: on a
  merge error, move the item to its review state, like a waiting merge.
* **A session that fails after `SessionStarted` leaks.** Errors between authoring the start and
  spawning the runner (runner.rs:466-562) leave a live session that holds the claim and a slot until
  the next daemon start.
* **A stop can hang.**
  * `Conversation::start` is awaited without watching `stopped` (runner.rs:1093).
  * A cancelled turn is awaited without a timeout.
  * `CancelHandle::cancel` uses `notify_waiters`, which loses a cancel that arrives early
    (`wf-harness/src/run.rs:338`).
  * Held permission requests are not answered `Cancelled` on cancel, which ACP requires.
  * Together these can leave a harness process alive and a ghost request in the inbox.
* **A failed diff gives an empty review.** If `git diff` fails while building the brief, the
  reviewer is briefed with an empty diff (runner.rs:1314) and may approve unseen work. Fail the
  session instead.
* **Races.**
  * The claim check and `SessionStarted` are separate storage jobs (runner.rs:408 vs 466), so a
    manual `session start` can race the dispatcher into two work sessions in one worktree.
  * `finish_session` is not serialized per session, so a submit racing a timeout can write
    duplicate moves.
  * A merge is not idempotent across a crash: a retry after `advance` but before `Merged` makes a
    second merge commit. Check `merge-base --is-ancestor` first.

### 1.3 Operating the daemon
* `wf daemon` runs only in the foreground and handles only Ctrl-C (`wf-cli/src/network.rs:481`), not
  SIGTERM from launchd or systemd.
* Its log is unstructured `eprintln!`, with no timestamps and no file.
* **`wf status` does not say whether a daemon runs (verified).** It prints `events: 7 heads: 1
  pending: 0`, which are internals. It should answer "is it working, and what should I do next?":
  daemon up or down, live, parked and stuck sessions, items given up on, inbox count.
* Suggested:
  * `wf daemon start|stop|status` (with a pid file and logs to `<data>/daemon.log` through
    `tracing`).
  * `wf status` rebuilt around next steps.
  * A desktop or terminal notification when something waits on you. Today you have to poll
    `wf inbox`.

### 1.4 Data safety
* There is no `wf export` (SPEC §4 promises `wf export --json`) and no import.
* When a store does not decode, the daemon prints "if it is from an older build, remove `<dir>`"
  (`wf-daemon/src/lib.rs:215`). It prints this for every error, including a transient
  `StoreError::Locked`.
* postcard has no field names, so changing an existing body's layout makes the whole store unreadable.
  While the schema still moves fast, that will happen.
* Fix: print the hint only for `Corrupt`, and add `wf export` / `wf import` that keep the signed
  bytes, before any real project's history lives in a store.

### 1.5 The network is on even when you are alone
* The daemon always starts a public iroh endpoint with n0 relays and address lookup, and joins a
  gossip topic per workforce, even with zero peers (`wf-daemon/src/lib.rs:163`, `peers.rs:248`).
* It costs about 270 extra crates in the daemon's tree and sends unexpected outbound traffic.
  SPEC's "sync can be a cargo feature" is not true today: the daemon's socket framing reuses
  `wf_net::frame`, and `StorageHandle` implements `SyncLog`.
* Recommendation: a runtime `Network::Off` (`node: Option<Arc<Node>>`), the default until a
  workforce has a second device. Making it a feature can come later.

## 2. CLI polish

What it feels like at a terminal today: the shape is right, and the gaps are help text, consistency
and filters.

### 2.1 Bugs and broken contracts
* **`wf item show --json` emits duplicate keys (verified).** `ItemDetail` flattens `ItemSummary` and
  declares `lane` and `labels` again (`wf-cli/src/view.rs:611-634`). The snapshot test has locked the
  duplicate in (`tests/snapshots/schemas__item_detail.snap` has `"lane"` twice).
* **Wrong or missing help (verified).**
  * `wf agent add --help` opens with "How much the agent does without a person…", the doc comment of
    the flattened `AutonomyArgs` (cli.rs:445). `agent edit` and `device edit` have the same leak.
  * `item diff` joins two sentences into one ("Show what the work… Show the work…").
  * These have no help at all: `item list|show|move|link|archive|unarchive`, the positionals of
    `comment` and `item move`, and most flags of `item add`, `agent add` (`--harness`, `--model`,
    `--capability`), `device edit` and `item link`.
  * `item add` and `item edit` use the editor paragraph as their one-line summary.
* **The default permissions disagree in three places (verified).** `agent add --help` says `allow`
  is the default, and so does `agent list`. The README says "Agents start with … `--permissions
  ask`". SPEC §5 shows `permissions = "allow"` but M2.1 risks says `ask` by default. Pick one and
  say it everywhere.
* **`--json` is not universal (SPEC §17 says it is).**
  * `session watch` rejects it.
  * `policy edit --json` emits a bare string.
  * Sessions, inbox, devices, members and `Done` have no snapshot tests.
* **`wf status --refold` fails while a daemon runs.** It opens the store directly and hits the lock
  (`workspace.rs:132,146`), which also breaks the rule that the daemon owns the store.
* **Lifecycle steps written by the CLI as two events.** `review --request-changes` writes `Review`,
  then decides on and writes an `ItemMoved` itself (`commands.rs:990-1010`, verified). `watch`
  writes N change requests and then a review. A failure in between leaves the item half-moved, and
  AGENTS.md puts this in `wf-core::lifecycle`.

### 2.2 Error messages
* `item move x bogus` says "the daemon refused: type `task` has no state `bogus`". It should list
  the valid states, and the `STATE` argument help should too.
* Archived items get three different refusals ("unarchive it to edit" / "unarchive it first" / "is
  archived").
* Commits are shortened by hand to 8 characters in five places, devices with `take(8)`.
* `Debug` output reaches users: `ended: {:?}` in view.rs:1172, the member role in devices.rs:91, and
  the `SessionEnded` line in `wf log`, per E2E-1.
* `wf mentions coder` refuses without `@`. Accepting the bare name is friendlier.
* `wf log` shows UTC ISO timestamps while every other view shows local short times (verified).
* `members`, `device list` and `log` print only headers when empty, while other lists say "no …".

### 2.3 Surface consistency
* **Spec drift.**
  * In SPEC §17 but missing: `export`, `search`, `invite member`, `owner add|transfer`,
    `policy diff|export`, `fork list`.
  * Present but not listed: `item check`, `item unarchive`, `policy show`, `mentions`.
  * Either mark the missing ones *later* in the spec or drop them; the spec should describe the
    binary.
* **Flag names.**
  * `wf review --request-changes` vs `wf comment --request-change` are one letter apart and easy to
    confuse.
  * Removal comes in four styles: `check --remove`, `--add-label` / `--remove-label`,
    `link --remove-depends-on`, and `agent edit --lane` replacing the whole list. `agent edit` also
    cannot clear `--model` or empty the capabilities.
* **Grouping.**
  * `review`, `comment` and `mentions` are top-level, while `move`, `link` and `check` are under
    `item`. Top-level for the things you type most is fine, but then say so in the help groups.
  * `members` is top-level while `device` is a group.
  * `fork` mixes a command and subcommands (`wf fork --exclude` vs `wf fork accept`).
  * `work` (agents only) sits beside `session` in help. Hide it or head it "inside a session".
* **Two ways to tick a step:** `item check 1 3` and `comment --step 1 --done`. Keep both, but write
  one event each (see 2.1).
* **`default_agent` lives in the signed, synced policy** (`wf-core/src/policy.rs:282`). Which agent
  *you* start by default is a personal or machine preference, so it belongs in the machine config.

### 2.4 Missing for day-to-day use
* `wf item cancel` (today: `item move <id> <the type's cancelled state>`), `wf agent remove`.
* Daemon management (1.3).
* Filters:
  * `item list --label/--lane/--priority`, a text match, `--limit`.
  * `session list --live/--item/--agent` (it grows forever).
  * `log --item/--since/--limit`.
* `session show` should include the last agent message or the failure class, not only the end
  reason.
* `wf init` without `-i` could default `--name` to the directory name.
* `wf harness list`, the detection `init` already does, and later probing whether a harness is
  logged in.

## 3. Simplification and naming

### 3.1 Names that collide (AGENTS.md: "step back and name it for its purpose")
| Name | Meanings today | Suggestion |
|---|---|---|
| **Blocker** | an open blocking comment (`CommentKind::Blocker`, `open_blockers`) *and* an unfinished dependency (`graph::Blocker`, `State::blockers`, `graph.rs:32,125`); they meet in `lifecycle.rs:111` | `UnfinishedDependency` / `unfinished_dependencies` for the graph |
| **Review** | review level (`ReviewName`, `Item::review`, `Change::Review`), verdict event (`EventBody::Review`), session role, state category, module | `ReviewLevelName` / `review_level`; event `Reviewed` (matches `Activity`, retires `Verdicted`) |
| **Waiting** | pending-parent key (`state.rs:266`) and what a person owes (`inbox.rs:11`) | `PendingOn` for the first |
| **Origin** | `Own/History` (`state.rs:63`) and `Body/Comment` (`item.rs:124`) | `TokenSource` for the second |
| **Comment** | event body and folded comment | fine if the event becomes `Commented` |
| **PermissionMode** | `wf_harness` (allow/deny) and `wf_core::autonomy` (allow/ask/deny); plus `proto::Answer`, `decide::Answer` | one `Permission` answer enum shared by harness, proto and deciders |
| **report** | `wf_core::report::report` formats error chains, while "report" was also a domain concept (SPEC §10) | `error_chain` |

Other leftovers:
* `PolicyError::ReviewWithoutBlocked` (`policy.rs:51`) is from the old "blocked" category.
* The `Raw*` prefix AGENTS.md bans: `RawBody`, `raw_item(s)`.
* Event names mix tenses: `ItemCreated` / `Merged` vs `Comment` / `Review` / `PolicySet`.
* `keys.rs` holds the whole data-dir layout. Name it `data_dir.rs`.
* **AGENTS.md itself refers to `soundings.toml` (verified), from another project.** It should say
  `config.toml` / the policy.

### 3.2 Stringly-typed and wildcard spots
* **Between `view` and `render` in the CLI**, state categories, comment kinds, session roles and
  inbox kinds travel as `String` and are matched with `_ =>` (`render.rs:67-95, 511-595`). Using
  the core enums with `Serialize` restores exhaustive matching. This is the biggest AGENTS.md
  violation in the codebase.
* `DeviceProfile.hardware: String` is split on commas at dispatch time (`dispatch.rs:81-90`), and
  only for work. Reviews ignore hardware, so a `gpu` step can never be matched. Make it a
  `BTreeSet<Requirement>` and add one `State::offered(device, agent)` for work, review and
  supervision.
* Wildcards on owned enums: `validate.rs:327,350,627,993`, `activity.rs:186,212`, and 13 in
  `wf-daemon/src/client.rs` on `Response`.
* `Done { event: String }` is filled with `String::new()` in five places, and holds a session id in
  one.

### 3.3 Things to delete
* **Policy config nothing reads:** `LaneConfig.claim/types`, `AssignmentConfig`, `AssignmentMode`,
  `Fallback`, `Lease`, `Transitions`, `MergeMode` (`policy.rs:157-241`). `Lease` is the only reason
  wf-core depends on `humantime`. Unknown tables are already tolerated, so stored policies keep
  parsing.
* `Mention::Session` is parsed but never resolves (`resolve.rs:188`), and its doc still says
  "Sessions arrive in M2".
* **Snapshot machinery that is never read back:** `covers` and the BLAKE3 `snapshot_key`
  (`redb_store.rs:84-90,233-237`). A single `meta["snapshot"]` row does the same.
* **Test-only API in public surfaces:** `EventStore::events()`, `SnapshotChange::Discard`,
  `State::canonical_principal`, `Policy::builtin_type_names`.
* `SharedReplica` (`wf-net/src/log.rs:72`) duplicates `StorageHandle` with blocking IO under a std
  mutex.

### 3.4 Duplication and long functions
* **wf-core.**
  * `self.policy().map(|d| &d.policy)` appears 13 times. Let `State::policy()` return `&Policy`.
  * The category check appears about 6 times; make the private `category_of` public.
  * There are three copies of prefix resolution.
  * Self-links are refused twice, under two names (`Invalid::SelfDependency`,
    `PolicyViolation::LinkToSelf`).
  * `check_actor` and `check_policy` are always called together; merge them into one "check before
    signing".
  * `check_policy` (245 lines) should split per event kind.
* **wf-daemon.** `runner.rs` (1,583 lines) mixes session start and end, merging, dispatch, parking,
  briefs and sandbox wiring. Split it into those four or five modules.
  * `begin_session` is 200 lines.
  * `start_session`, `start_review` and `start_supervision` only forward a role.
  * The worktree path is built in three places, and again in the CLI (`commands.rs:1152`,
    `session.rs:235`).
* **wf-cli.**
  * `commands.rs` (1,552) splits naturally into `item`, `vcs` (diff/checkout/path), `comment`,
    `review`/`work`, `agent`, `policy`/`log` and `output`.
  * `view.rs` (1,528) splits into `view/{item,event,session,inbox,status}`.
  * The `Waiting` → text mapping exists twice (`view.rs:1444`, `watch.rs:108`).
  * `transcript.rs` has its own colours and width logic instead of `render::style`.
  * `watch` builds a clap `ReviewArgs` to call `review()`.

### 3.5 Domain logic that has leaked out of `wf-core::lifecycle`
* After a merge outcome: conflict → open, dirty or moved target → review (`runner.rs:922-952`).
* `Finish` → reason, actor and comment (`runner.rs:624-658`).
* Approved work without commits → done (`runner.rs:1475`).
* `review --request-changes` → open (CLI, 2.1).
* The "parked" session status (`view.rs:1406`) and the item list ordering (`commands.rs`).
* Suggested: `State::after_merge(item, outcome)` and a pure `Finish → (EndReason, author, note)`.

### 3.6 Purity
* `$signer::generate()` uses OS randomness inside wf-core (`identity.rs:122`). Callers should pass
  the key in, or generation should sit behind a feature.
* `brief.rs` embeds exact `wf` command lines in core strings. It is pure, so this is acceptable,
  but a flag rename in the CLI silently desyncs the prompts.
  * Keep the check that brief commands parse (there is one); extend it to the nudge.

## 4. Decisions worth revisiting

**Ending sessions on every daemon restart.**
* For: simple, honest, no half-states.
* Against: on the machine where wf is developed, restarts are constant, and each one throws away
  every agent's context and, today, counts as a failure.
* **Recommendation:** keep the ending, but as `Interrupted`, not `Failed`; add a stable agent-side
  `wf` binary; try `session/load` for resuming later.

**An exact socket protocol version.**
* For: clean refusals.
* Against: it couples every agent's `wf` to the daemon's build.
* **Recommendation:** pin agents to the daemon's binary (1.1) instead of making the protocol
  additive. That is cheaper and fixes the real case.

**Shipping the whole `State` to the CLI on every command.**
* What happens: `Request::State` serializes the full fold (`proto.rs:154`), `author` re-fetches it,
  and `wf watch` polls it twice a second.
* For: one code path for local and daemon mode, and queries stay typed Rust.
* Against: cost grows with the log, and `watch` re-transfers everything every 500 ms.
* **Recommendation:** fine for months of solo use. When it hurts, add `events_since` plus a local
  fold cache, or a subscription, which a TUI wants anyway. Not urgent.

**`Finish` as one enum for agent verdicts and daemon interruptions.**
* What happens: any socket client can send `Failed` or `GaveUp`, and the agent/daemon split is
  encoded twice.
* **Recommendation:** split it into `AgentFinish` (submit, release, reviewed, supervised: wait for
  the turn, authored as the agent) and `Interruption` (stop, moved on, timed out, failed, gave up:
  now, authored by the daemon). Cheap, and it removes illegal states.

**Merging into the user's checked-out target.**
* What happens: a clean `main` is fast-forwarded under your editor, and a dirty one makes merges
  wait. A developer's main checkout is often dirty, and E2E-1 lost 8 minutes to this.
* Options:
  * (a) Advance the ref only and tell the user their checkout is behind.
  * (b) Merge only when the checkout is clean, as now, but show in `wf status` *which files* block
    it.
* **Recommendation:** (b) now. Consider (a) as a policy option once people work in the main
  checkout while agents run.

**Judges as one long-lived harness per agent.**
* For: low latency.
* Against:
  * Every session's requests queue behind one mutex (up to 120 s each).
  * A prompt injection stays in the context for the next 50 decisions.
  * Judges run outside Fence.
* **Recommendation:** prefer the model decider; when an agent judge is used, give it a fresh
  session per request or a much smaller `turns`.

**The `Option<Workforce>` inside `State`.**
* What happens: about 30 accessors carry a `?` for the "before genesis" case.
* **Recommendation:** worth it only if it falls out of other work. A `State` that exists only after
  genesis would remove that noise, but `receive` must then own the transition. Low priority.

**The network on by default.** See 1.5. Default it off for a single device.

**postcard for stored events.** Keep it, because the signed bytes need canonical encoding. Add
export and import (1.4) and a version byte per body before the schema next changes.

## 5. Suggested order

Small commits, one per bullet, roughly in this order.

**A: no silent stalls (most value per line).**
1. `EndReason::Interrupted` for restarts; it does not count toward giving up.
2. Role-aware nudges and give-up; `reviewable` respects given-up.
3. Merge errors move the item to review; errors after `SessionStarted` end the session `Failed`.
4. Bounded stop and cancel; answer held permissions with `Cancelled`.
5. Atomic claim and start; serialized `finish_session`; idempotent merge.
6. A given-up item says so in `item show` and `status`, with the command to retry.

**B: operating it.**
1. Agents run the daemon's own copy of `wf`.
2. `wf daemon start|stop|status`, `tracing` to a log file, SIGTERM.
3. `wf status` answers "is it working, what next".
4. `wf export` / `wf import`; the "remove the directory" hint only on `Corrupt`.
5. `Network::Off` by default for a single device.

**C: CLI polish.**
1. Fix the duplicate JSON keys and the leaked or missing help texts.
2. One permissions default, said everywhere.
3. Move the request-changes move into `wf-core`, as one decision.
4. Error messages that list valid values; local times in `log`; empty states.
5. `item cancel`, `agent remove`, `session list --live`, `item list` filters.
6. Typed enums between view and render.
7. Update SPEC §17 to the actual surface.

**D: tidy-up, whenever you touch the area.**
1. Renames: Blocker/dependency, review level, `Raw*`, `report`, AGENTS.md's `soundings.toml`.
2. Delete unused policy config and snapshot keys.
3. Split `runner.rs`, `commands.rs` and `view.rs`.

After A and B, the next real test is an E2E-2 on wf itself: a week of normal work with a coder and a
reviewer on a non-toy item, restarting the daemon as development requires. That run will show what
this review could not.
